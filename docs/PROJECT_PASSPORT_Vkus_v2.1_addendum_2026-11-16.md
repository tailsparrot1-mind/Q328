# Дополнение к паспорту Vkus — 16.11.2026
Версия дополнения: 2.1
Базовый паспорт: `docs/PROJECT_PASSPORT_Vkus_v2.0.md` в `tailsparrot1-mind/Q328`, ветка `feature/vkus-328-marketplace-board`.

Это дополнение обязательно читать вместе с основным паспортом. Оно фиксирует новые требования пользователя и имеет приоритет над более ранними противоречащими реализациями.

## 1. Новые замечания пользователя: три критические ошибки сборки

### 1.1. Доска объявлений — референс, а не самостоятельный Tkinter-дизайн
**Требование пользователя:** доска объявлений должна быть оформлена на основе предоставленного пользователем изображения-референса. Само изображение используется как визуальная основа/фон, а рабочие кнопки, поля и интерактивные элементы накладываются поверх него в соответствующих местах. Нельзя заменять референс заново придуманным стандартным интерфейсом Tkinter или упрощённым макетом.

**Критерии приёмки:**
- Найти и использовать именно исходный референс пользователя из истории/ассетов; не рисовать замену и не угадывать его композицию.
- Сопоставить готовый экран с референсом по масштабу, позициям, размерам, цветам, шрифтам, свечению, карточкам и отступам.
- Интерактивные области должны совпадать с предусмотренными на референсе местами.
- Не считать наличие отдельного окна или работающих кнопок доказательством соответствия дизайну.
- Если оригинальный файл референса не найден, остановить визуальную реализацию и сообщить, что конкретно отсутствует; не подменять его своим вариантом.

### 1.2. Навигация доски объявлений
**Требование пользователя:** «Доска объявлений» — самостоятельный пункт главной левой боковой навигации Vkus, на одном уровне с пунктами «Сообщения», «Поиск», «Биржа», «Мониторинг», «Настройки».

**Запрещённое размещение:** кнопка/ссылка доски объявлений внутри рабочей области «Умного поиска», над «Найти ЦА» и блоком источников. Такое размещение ошибочно и должно быть удалено.

**Критерии приёмки:**
- Пункт виден слева в основной навигации постоянно в том же визуальном ряду/стиле, что и соседние разделы.
- Открывает экран доски объявлений.
- Не дублируется как отдельная CTA-кнопка над поиском.
- Существующие пункты и их маршруты не ломаются.

### 1.3. Покупка лицензии — встроенная витрина и запросы из приложения
**Требование пользователя:** при нажатии «Купить лицензию» витрина должна открываться внутри самого приложения Vkus, а не во внешнем Chromium/Chrome и не через промежуточную raw/githack-ссылку или стороннюю страницу-переадресацию.

**Архитектурное требование пользователя:** сетевые POST/GET-запросы к серверному API, базе данных и платёжной интеграции инициирует нативная серверная/клиентская логика Vkus, а не JavaScript загруженной веб-страницы в браузере. Встроенная витрина является интерфейсом выбора тарифа/оформления, но не доверенной стороной для платежей, выдачи лицензии или авторизации API.

**Обязательные меры безопасности:**
- Не открывать покупку внешним браузером и не передавать контроль API странице/JavaScript.
- Все запросы приложения выполнять через нативный сетевой слой с HTTPS и строгой проверкой TLS-сертификата/цепочки доверия; не отключать проверку сертификатов.
- Не хранить секретные ключи, service-role credentials, платёжные секреты или мастер-ключи в клиенте, HTML, JavaScript, ZIP или репозитории.
- Сервер обязан самостоятельно проверять пользователя, права, сумму, тариф, состояние заказа и подпись/подтверждение платёжного провайдера.
- Клиент не может сам объявить платёж успешным или активировать лицензию по ответу, который он может подделать.
- Защитить операции создания заказа/активации от повторного воспроизведения (идемпотентность, уникальные идентификаторы, серверная проверка статуса).
- Учесть MITM-сценарий пользователя: в публичной Wi-Fi сети возможен мониторинг/подмена при компрометации доверия TLS на устройстве. Поэтому нельзя считать встроенный браузер или простую замену Chromium достаточной защитой. Рассмотреть certificate/public-key pinning с корректной ротацией и резервной стратегией, не ослабляя стандартную проверку TLS.
- Любой WebView, если он необходим только для визуального интерфейса, не должен иметь мост/доступ к секретам и не должен самостоятельно вызывать привилегированные API. Предпочтительно реализовать витрину нативными компонентами приложения, если это совместимо с утверждённым дизайном.

**Платёжный провайдер:** ранее в паспорте зафиксировано согласование Robokassa + Supabase, но аудит 15.11.2026 показывал, что фактически найден Taplink webhook, а Robokassa не была подключена. Не выдавать Taplink за согласованную Robokassa-интеграцию и не переключать провайдера без подтверждения пользователя. До реализации сверить текущее состояние Supabase, существующие Edge Functions и миграции. Не выполнять реальные списания без отдельного согласования.

## 2. Порядок исправления и сдачи
Пользователь поручил исправить все три ошибки в актуальной сборке, записать изменения в GitHub и только после этого сформировать и передать ZIP.

Порядок обязателен:
1. Перед изменениями перечитать основной паспорт целиком и это дополнение, проверить последние решения пользователя и актуальный HEAD исходников.
2. Установить точный актуальный исходный архив/исходники. Не работать поверх случайной или устаревшей сборки.
3. Найти оригинальный референс доски объявлений. Если его нет в доступных файлах/истории, не придумывать дизайн и запросить только недостающий референс.
4. Исправить дизайн доски по референсу, расположение пункта в левой навигации и встроенный поток покупки с нативным сетевым слоем.
5. Сохранить остальные функции, визуальный стиль и архитектуру Vkus; не проводить несогласованный редизайн.
6. Провести проверки: статические/модульные; реальный запуск приложения; визуальная сверка экрана доски с референсом; проверка левого маршрута; тест открытия витрины внутри приложения; тест, подтверждающий, что API-запросы выполняет нативный слой, а не JavaScript/Chromium; TLS/ошибочные сертификаты; серверная проверка заказа/платежа/лицензии. Не выполнять реальную оплату без отдельного разрешения.
7. Сначала записать исправленный исходный код и документацию в GitHub и перечитать их из репозитория. Только после подтверждённой записи формировать ZIP.
8. ZIP должен соответствовать именно зафиксированному GitHub-коммиту. Проверить ZIP integrity и SHA-256.
9. Сдать ZIP, реальный скриншот запущенного приложения и отчёт с отдельными статусами ПРОВЕРЕНО / ЧАСТИЧНО ПРОВЕРЕНО / НЕ ПРОВЕРЕНО. Не подменять скриншот реального запуска мокапом или скриншотом отдельного компонента.

## 3. Ошибки реализации, которые нельзя повторять
- Не подменять предоставленный пользователем референс собственным Tkinter-экраном.
- Не размещать пункты главной навигации внутри другого раздела.
- Не открывать магазин через внешний браузер, raw/githack redirect или промежуточную страницу.
- Не заявлять, что приложение защищено от MITM только потому, что браузер заменён встроенным окном.
- Не считать код маркетплейса в архиве доказательством правильного расположения/визуальной реализации.
- Не формировать ZIP до фиксации исправлений в GitHub и проверки чтением.

## 4. Журнал
- 2.1 — 16.11.2026: пользователь указал три критические ошибки: неверная реализация доски объявлений (Tkinter вместо референса с наложенными интерактивными элементами), неверное размещение пункта доски внутри «Умного поиска» вместо левой навигации, и внешний запуск покупки лицензии через Chromium/raw redirect вместо встроенной витрины и нативных POST/GET-запросов. Добавлены критерии визуальной/функциональной приёмки и требования безопасности для MITM-сценария.
